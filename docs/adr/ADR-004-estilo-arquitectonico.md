# ADR N.° 04 · Monolito modular con núcleo hexagonal en los módulos que tocan dinero

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado (30/10/2026) |
| Contexto | El ADR N.° 03 fijó una sola aplicación Django. Faltaba decidir su estructura interna. Los drivers del ADR N.° 02 ponen primero la fiabilidad de pagos y fechas, que depende de poder probar las reglas a fondo y sin base de datos. El núcleo ya tenía puertos de salida, pero los casos de uso vivían dentro de `dominio/` y no había adaptadores reales: las pruebas solo corrían contra dobles (DT-02) y el comprobante duplicado no lo protegía la base de datos (DT-01). La guía advierte que poner puertos en todo puede duplicar archivos sin necesidad. |
| Alternativas consideradas | **A. Capas al estilo Django:** modelos con la lógica, vistas y plantillas; las reglas dentro de los modelos del ORM. **B. Hexagonal en todo el sistema:** puertos y adaptadores también para planes, cuentas y reportes. **C. Monolito modular con núcleo hexagonal selectivo:** puertos y adaptadores solo donde están las reglas de dinero y de fechas (socios, pagos, membresía); los módulos que son casi CRUD (planes, cuentas) usan Django directamente. |
| Matriz (alto/medio/bajo) | Fiabilidad de pagos y fechas: A medio, B alto, C alto. Consulta disponible en recepción: A alto, B alto, C alto. Seguridad: A alto, B alto, C alto. Costo en archivos y complejidad: A alto (el menor costo), B bajo, C medio. |
| Decisión | Se adopta la alternativa C: un monolito modular cuyo núcleo (`dominio/` y `aplicacion/`) no conoce Django y se conecta a la infraestructura por puertos; los adaptadores viven en `infraestructura/`. Los casos de uso son clases concretas, sin interfaz propia, porque solo hay una implementación. |
| Consecuencias | A favor: las 70 pruebas del núcleo corren en 0,07 s sin Django ni base de datos; las mismas pruebas de contrato validan los repositorios en memoria y los de Django ORM; la base protege RN-06 con un índice único parcial y QA-05 pasa 100 de 100 contra PostgreSQL. En contra: los repositorios ORM duplican la forma de las entidades (hay que mapear de modelo a entidad), y quien llegue al proyecto debe aprender dónde va cada cosa; la regla se vigila con `tests/nucleo/test_arquitectura.py`. Mientras no exista el módulo de cuentas, los usuarios se guardan desde el repositorio de pagos (DT-11). |
| Alternativas descartadas | **A** se descarta porque obliga a probar las reglas de dinero con la base de datos y mezcla la lógica con el ORM, que es justo lo que produjo la duplicación del prototipo (DT-04). **B** se descarta por sobreingeniería: planes y cuentas no tienen reglas que justifiquen un puerto, y Django ya trae su propia autenticación; poner interfaces ahí solo agregaría archivos. |
