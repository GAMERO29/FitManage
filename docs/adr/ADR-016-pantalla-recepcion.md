# ADR N.° 16 · La pantalla de recepción es una página estática del mismo origen que consume la API, y el primer arranque crea los planes y la primera cuenta

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado (6/11/2026). Reemplaza la parte del ADR N.° 03 que hacía de las plantillas de Django la interfaz principal. El resto del ADR N.° 03 (una sola aplicación, un solo despliegue) sigue vigente. |
| Contexto | Al preparar la demostración de la Guía 16 se encontró que la producción solo tenía la API: las plantillas del ADR N.° 03 nunca se construyeron, porque desde la Guía 6 todo el trabajo se hizo sobre el contrato `/api/v1`, y la vista móvil solo tiene su cliente HTTP y su contrato Pact. Además, la base de producción no tenía planes ni cuentas, y el plan gratuito de Render no tiene Shell para crearlas. Es decir: el sistema estaba verificado, pero el gimnasio no podía usarlo. Fuerzas: una sola persona y pocas horas; el ADR N.° 06 ya define cómo autentica un cliente de la API desde el navegador (token en memoria, renovación con cookie `HttpOnly`); la Ley 1581 todavía no tiene el texto de autorización aprobado (DT-10); costo 0 (R-01). |
| Alternativas consideradas | **A. Plantillas de Django con sesión**, como decía el ADR N.° 03: un segundo mecanismo de autenticación, formularios y CSRF, y reglas de presentación duplicadas con las de la API. **B. Una SPA con framework (React, Vue) y su propia compilación:** un segundo proyecto de Node para tres pantallas. **C. Tres archivos estáticos (HTML, JS y CSS) servidos por la misma app**, que solo llaman a `/api/v1` y no tienen lógica de negocio. **D. Crear el administrador con una migración de datos:** la clave quedaría en el código o en la historia de migraciones. **E. Un comando idempotente que corre en cada arranque** y lee la cuenta de variables de entorno del PaaS. |
| Decisión | Se eligen **C** y **E**. La pantalla (`infraestructura/web/`) cubre el recorrido de recepción: iniciar sesión, consultar el estado (CU-03), registrar un socio (CU-02) y registrar un pago (CU-04). No calcula fechas ni estados: todo lo calcula el servidor, como pide RN-05. El token vive en una variable; se renueva una vez con la cookie y, si no se puede, se vuelve a pedir la sesión. Los datos de la API se escriben con `textContent`. La página se sirve con `Content-Security-Policy` que solo permite el mismo origen y prohíbe scripts en línea, marcos y envíos a otros sitios. El pago genera una `Idempotency-Key` al abrir el formulario y la reutiliza en los reintentos (PA-11). El registro de socio muestra que el texto de autorización está pendiente (DT-10) y pide usar solo datos de prueba. `preparar_gimnasio` crea los cuatro planes de referencia si no hay ninguno, y la primera cuenta de administrador desde `FITMANAGE_ADMIN_NOMBRE`, `FITMANAGE_ADMIN_CORREO` y `FITMANAGE_ADMIN_CLAVE` (mínimo 12 caracteres) si no existe ninguna. Nunca modifica lo que ya existe y nunca imprime la clave. |
| Consecuencias | A favor: la demostración recorre el flujo real con la API ya cubierta por la suite completa, el contrato y Pact; no hay un segundo mecanismo de autenticación; la prueba de extremo a extremo con Chromium registró un socio y un pago, y dos envíos seguidos del formulario crearon un solo pago. También encontró un defecto real (BUG-01, issue #38). En contra: no hay pruebas automáticas del JavaScript en el pipeline, solo pruebas que revisan sus reglas de seguridad (sin `localStorage`, sin `innerHTML`, sin recursos externos) y la prueba de extremo a extremo manual; no hay pantalla para crear planes ni personal (HU-04 sigue pendiente, DT-24); y la cuenta inicial depende de que alguien configure tres variables en Render. |
| Cuándo revisar esta decisión | Cuando se implemente la vista sin conexión de QA-02 (hito H4): el Service Worker y la caché pueden reemplazar esta página o crecer desde ella. Si la pantalla pasa de unas pocas vistas, reconsiderar la alternativa B. |
