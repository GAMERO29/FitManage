# ADR N.° 20 · Bloquear TRUNCATE sobre la auditoría con un disparador, con una excepción solo para las pruebas

| Campo | Contenido |
| --- | --- |
| Estado | Propuesto (27/11/2026, Software III · Guía 01). Se implementa y verifica en la Guía 14 con la migración 0004. Complementa el ADR N.° 19 sin cambiar su regla. |
| Contexto | El ADR N.° 19 protege la tabla `auditoria` contra UPDATE y DELETE, pero no contra TRUNCATE (consecuencia 2 de ese ADR). La Guía II-04 lo convirtió en el defecto DEF-03: el caso CP-24 vació la tabla con un `TRUNCATE` y la prueba falló. El plan de piloto lo pone como condición previa. La razón de no haberlo bloqueado fue que pytest-django vacía las tablas con TRUNCATE entre las pruebas que usan transacciones reales (las de concurrencia). Requisitos vinculados: RNF-05 y RN-07 (rastro de quién anuló y por qué) y el escenario AQ-04 de la ficha FPI-III-01. |
| Alternativas consideradas | **A. Disparador `BEFORE TRUNCATE` en PostgreSQL** que rechaza la orden, salvo cuando la sesión declara `fitmanage.permitir_vaciado = 'si'`, un ajuste que solo configura el `conftest.py` de las pruebas. Ventajas: no depende de Render; una sola migración; la misma idea del ADR 19. Desventajas: quien tenga las credenciales del dueño de la base puede declarar el ajuste o borrar el disparador. **B. Separar roles en la base:** la aplicación se conecta con un rol sin permiso de TRUNCATE ni de ser dueño de las tablas; las migraciones usan otro. Ventaja: también frena a un atacante con las credenciales de la aplicación. Desventajas: hoy la aplicación usa el único usuario que entregó Render, dueño de todas las tablas, y no está probado que ese plan permita crear un rol más; exige dos `DATABASE_URL` y cambiar el arranque (`docker/arrancar.sh` migra con las mismas credenciales con las que sirve). |
| Decisión | Se elige **A** ahora y **B** queda como paso del hito H1, cuando la base pase a un plan pago y se compruebe que permite crear un rol con menos permisos. En SQLite no existe TRUNCATE: el disparador de DELETE del ADR 19 ya cubre el `DELETE FROM auditoria` sin condición. |
| Consecuencias | A favor: se cierra DEF-03 para la aplicación, para una consola de Django y para un error humano con `psql`. La prueba CP-24 de la Guía II-04 pasa a ser una prueba de regresión. En contra, y aceptado: (1) no protege contra el dueño de la base, que puede declarar el ajuste o desactivar el disparador; para eso está B. (2) Las pruebas dependen de declarar el ajuste en cada conexión; si alguien quita esa línea del `conftest.py`, las pruebas de concurrencia fallan al vaciar la base, y ese fallo es visible. (3) `TRUNCATE ... CASCADE` sobre `pagos` o `socios` también se rechaza si arrastra a `auditoria`; no hay un caso de uso que lo necesite. |
| Plan de comprobación | En la Guía 14: (1) prueba de integración en PostgreSQL que ejecuta `TRUNCATE auditoria` sin el ajuste y espera el error del disparador, y comprueba que las filas siguen ahí; (2) la misma orden con el ajuste se acepta (es lo que usa pytest-django); (3) la suite completa en PostgreSQL pasa, incluidas las pruebas de concurrencia; (4) la migración se ensaya hacia adelante en una copia con datos ficticios, como en la Guía II-03. |
| Cuándo revisar esta decisión | Al llegar al hito H1 (base paga): entonces se implementa B y este disparador queda como segunda barrera. También si el rastro tuviera que vivir fuera de la base (revisión del ADR N.° 19). |
