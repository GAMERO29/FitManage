# ADR N.° 07 · Pirámide de pruebas con base efímera real y dobles solo en las fronteras externas; el contrato se verifica en cada respuesta y con Pact

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado (31/10/2026) |
| Contexto | Hasta la Guía 6 la API solo existía como contrato y la colección de Postman corría contra un mock. Al implementar 12 operaciones aparece el riesgo que describe la Guía 7: 87 pruebas unitarias verdes no dicen nada sobre el ORM, las transacciones, la traducción de errores a códigos HTTP ni si la respuesta cumple el contrato. El driver número uno (QA-05) es justo una propiedad de la integración con PostgreSQL (el índice único parcial). La única dependencia externa de la API es el SMTP del hosting para restablecer contraseñas (DAD 8.2); la otra frontera es la hora del servidor (QA-03). |
| Alternativas consideradas | **A. Integración con repositorios en memoria:** rápida, pero no prueba el ORM, ni el índice parcial, ni la zona horaria de la base. **B. Integración contra la API real y la base efímera de pytest-django, con dobles solo en el reloj y en el backend de correo; contrato validado en cada respuesta con openapi-core; Pact para la vista móvil.** **C. Pocas pruebas de integración y muchas E2E con navegador:** el MVP todavía no tiene plantillas, y serían lentas y frágiles. **D. Base de desarrollo compartida con datos fijos:** las pruebas dependerían de lo que alguien haya dejado en la base. |
| Decisión | Se elige **B**. Las pruebas de integración usan el cliente de Django sobre la base que crea y destruye pytest-django (SQLite en memoria en local, `test_fitmanage` en el contenedor PostgreSQL 16 de CI), y `test_la_base_de_estas_pruebas_es_efimera` falla si algún día apuntan a la de desarrollo. El `ClienteAPI` de `tests/apoyo_api.py` valida cada respuesta contra `docs/api/openapi.yaml`. La aceptación (PA-01 a PA-11 del DDS) se escribe en Gherkin con pytest-bdd sobre la misma API. El contrato con la vista móvil se define desde el consumidor con Pact y se verifica contra `live_server`. |
| Estrategia de mocking e integración para APIs externas | Toda dependencia externa entra por un puerto del dominio (`CorreoSaliente`, `Reloj`) y un adaptador en `infraestructura/`. En las pruebas se reemplaza **solo el adaptador o su transporte**, nunca el caso de uso, la calculadora ni los repositorios: el correo usa el backend en memoria de Django (`locmem`) y `CorreoCaido` simula el SMTP caído (503 sin tocar la cuenta); el reloj se fija con `RelojFijo` desde `contenedor.reloj`. Si mañana entra una API HTTP (por ejemplo, una pasarela de pagos), tendrá su puerto, su adaptador con `requests` y en las pruebas se interceptará el transporte HTTP, más una prueba de contrato con el proveedor si este la ofrece. |
| Consecuencias | A favor: al escribir y correr las pruebas, antes de llegar a `main`, aparecieron 6 defectos reales: los intentos fallidos se perdían por el rollback de la transacción, el contrato decía `PA` y el dominio `PASAPORTE` (y 15 caracteres donde el pasaporte admite 20), el rol Entrenador no tenía 403 en el contrato, los JWT usaban el reloj del negocio para `exp`, y la vista móvil suponía dos cosas falsas que Pact rechazó (que todo estado trae `venceEl` y que el 401 es `application/json`). La suite completa corre en unos 7 s y no necesita servicios externos. En contra: las pruebas de integración son más lentas que las unitarias (75 en 3 s frente a 87 en 0,1 s), dependen de pytest-django y de openapi-core, y la verificación Pact agrega pact-python (binario Rust) y Node para el consumidor. Por ahora no hay pruebas E2E de navegador: se agregarán, pocas, cuando existan las plantillas. |
| Alternativas descartadas | **A:** dejaría sin probar QA-05 y la traducción de `IntegrityError`, que fallan solo con la base real. **C:** invierte la pirámide; cada cambio de CSS rompería pruebas de reglas de negocio. **D:** viola la regla de oro de la Guía 7 y hace que el resultado dependa del orden de ejecución. |
