# ADR N.° 10 · Imagen multietapa sobre `python:3.12-slim-trixie` que corre sin root, y Docker Compose con la base en un volumen dentro de una red interna

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado (2/11/2026) |
| Contexto | Desde la Guía 3 (DT-08) había un `Dockerfile` de una sola etapa: instalaba también las herramientas de desarrollo, copiaba todo el repositorio y su comando era `pytest`. Servía para probar, no para desplegar. Pesaba 282 MB, llevaba dentro las pruebas, el prototipo y, si existía, el archivo `fitmanage.sqlite3`, que `.dockerignore` no excluía. El ADR N.° 09 ya publica una imagen por commit, así que esa imagen tiene que ser la de producción. Fuerzas: un PaaS pequeño donde el peso y el arranque importan, la regla de oro de la guía (ninguna credencial en el `Dockerfile` ni en el `docker-compose.yml`), las dependencias nativas (`psycopg[binary]` trae `libpq` compilada) y una sola persona para mantenerlo. |
| Alternativas consideradas | **A. Seguir con una etapa**, solo cambiando el comando a gunicorn. **B. Multietapa sobre `python:3.12-slim-trixie`** (Debian, glibc). **C. Multietapa sobre `python:3.12-alpine`** (musl). **D. Imagen *distroless* de Python.** |
| Decisión | Se elige **B**. El `Dockerfile` tiene tres etapas: `construccion` instala solo `requirements.txt` en `/opt/venv`; `pruebas` agrega las herramientas de desarrollo y el repositorio y corre `pytest` (CI la usa y no se publica); `produccion` copia el entorno virtual y únicamente el código del servidor (`config`, `dominio`, `aplicacion`, `infraestructura`, `manage.py` y el contrato OpenAPI que valida cada petición). Corre como el UID 10001, con el código de root en solo lectura para el proceso, healthcheck sobre `/api/v1/salud` y gunicorn como comando. La capa de dependencias va antes del código, así que cambiar código no vuelve a instalar nada. `docker-compose.yml` levanta `db` (PostgreSQL 16, volumen `datos`), `migrar` (un paso único) y `app` (`read_only`, sin capacidades de Linux, `no-new-privileges`, publicada solo en `127.0.0.1`). La base vive en la red `interna`, marcada `internal: true`, y las tres claves salen de `.env`, que está en `.gitignore`. |
| Consecuencias | A favor: la imagen de producción pasó de 282 MB a 206 MB (−27 %) y ya no trae pytest, las pruebas, el prototipo ni archivos de base local; el pipeline lo verifica en cada PR. Reconstruirla tras cambiar solo código tarda 2 s porque la capa de dependencias viene de la caché. Compose se probó en CI: los tres servicios sanos, la base sin salida a internet, el plan insertado sobrevive a `down` + `up` y desaparece con `down -v`, y la suite completa pasa contra ese PostgreSQL. En contra: Alpine habría pesado 133 MB (73 MB menos); se renuncia a esa diferencia (ver descartadas). Hay dos imágenes que mantener coherentes (`pruebas` y `produccion`), aunque comparten la etapa base. La imagen base está referida por etiqueta y no por digest, así que puede cambiar con un parche de Debian o de Python; queda para Dependabot. |
| Alternativas descartadas | **A:** mantiene las herramientas de desarrollo y el código de pruebas en lo que se despliega, y cualquier vulnerabilidad de esas herramientas viaja a producción. **C:** en la prueba de CI funcionó (`psycopg` encontró una rueda binaria para musl), pero es un riesgo de cada actualización: cuando una dependencia no publique rueda para musl, pip intentará compilarla y la imagen dejará de construir. Además, musl se comporta distinto que glibc en DNS, zonas horarias y rendimiento de la asignación de memoria, y esta aplicación depende de la hora de Bogotá (QA-03). 73 MB menos no pagan ese riesgo en un PaaS que cobra por memoria y no por disco. **D:** no trae shell, lo que complica el healthcheck y la depuración en un proyecto que todavía no tiene observabilidad, y sus imágenes de Python van detrás de las versiones oficiales. |
| Cuándo revisar esta decisión | Si el PaaS elegido cobra por tamaño de imagen o tarda en arrancarla, si `psycopg` deja de publicar ruedas para glibc, o cuando se agregue escaneo de vulnerabilidades de la imagen y la base slim aparezca con hallazgos que Alpine no tenga. |
