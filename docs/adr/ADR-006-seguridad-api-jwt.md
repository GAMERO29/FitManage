# ADR N.° 06 · La API `/api/v1` se protege con JWT de acceso corto y renovación en cookie `HttpOnly`; la interfaz web sigue con la sesión de Django

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado (31/10/2026) |
| Contexto | El ADR N.° 03 dejó una sola aplicación Django con plantillas y un único endpoint JSON para la caché sin conexión. Al escribir el contrato de la Guía 6 (`docs/api/openapi.yaml`), la API creció a 12 operaciones porque la vista móvil sin conexión, que corre en el celular del personal, también necesita registrar socios y pagos cuando vuelve la señal, y porque una futura integración (por ejemplo, el contador o una pasarela) no puede depender de las plantillas. Las plantillas siguen siendo la interfaz principal, así que esto no reabre la alternativa «API + SPA» que el ADR N.° 03 descartó. Fuerzas: QA-04 (ninguna ruta de administrador responde a la recepcionista), un celular se puede perder, la cuenta bloqueada debe dejar de funcionar pronto, costo 0 (R-01) y una sola persona desarrollando. |
| Alternativas consideradas | **A. Sesión de Django también para la API:** cookie de 8 horas (un turno) y CSRF en cada escritura. **B. JWT de acceso de 15 minutos (HS256) + token de renovación opaco de 8 horas en cookie `HttpOnly; Secure; SameSite=Strict`, que rota en cada uso y se guarda por dispositivo.** **C. JWT RS256 emitido por un proveedor de identidad externo** (Auth0, Cognito o Keycloak). **D. Llaves de API fijas por dispositivo.** |
| Decisión | Se elige **B**. Todo endpoint exige `bearerAuth` por defecto (`security` global del contrato); solo `/salud` y `/auth/token` lo anulan con `security: []`, y `/auth/renovacion` usa la cookie. El token lleva `sub`, `rol`, `iss=fitmanage`, `aud=fitmanage-api`, `iat`, `exp` y `jti`; se rechaza `alg: none` y cualquier algoritmo distinto de HS256, y se valida `iss`, `aud` y `exp` con 30 segundos de tolerancia. La clave de firma vive en la variable de entorno `JWT_CLAVE`, distinta de `SECRET_KEY`, con `kid` para poder rotarla. El token de acceso se guarda en memoria (la página o el Service Worker), nunca en `localStorage`. El `rol` del token sirve para mostrar u ocultar opciones, pero las operaciones de administrador (anular y reportes) vuelven a consultar el rol en la base antes de ejecutar. |
| Consecuencias | A favor: el contrato declara la seguridad de cada endpoint sin depender de cookies de sesión ni de CSRF; si se pierde un celular, el administrador revoca su token de renovación y ese dispositivo queda fuera en máximo 15 minutos sin cerrar la sesión del PC de recepción; una cuenta bloqueada no puede renovar; el costo sigue en 0 USD porque emite y verifica el mismo proceso. En contra: hay dos mecanismos de autenticación que mantener y probar (sesión para las plantillas y JWT para la API); un token robado sirve hasta 15 minutos; se agrega la tabla `renovaciones` (dispositivo, `jti`, vence, revocado) y la clave `JWT_CLAVE` que hay que custodiar. |
| Alternativas descartadas | **A:** una cookie de 8 horas en un celular perdido da 8 horas de acceso, y revocarla cierra también la sesión del PC; además, cada escritura desde el Service Worker tendría que manejar el token CSRF. **C:** RS256 solo se justifica si otro sistema tiene que verificar los tokens sin conocer la clave; aquí emite y verifica la misma aplicación, y un proveedor externo agrega costo, una dependencia de internet en el inicio de sesión (R-03) y otra cuenta que administrar. **D:** una llave fija no expira, no lleva rol y, si se filtra, sirve hasta que alguien note el problema. |
| Cuándo revisar esta decisión | Si una integración externa necesita verificar tokens por su cuenta (pasar a RS256 con JWKS), si el gimnasio abre una segunda sede con otro servidor o si la vista móvil deja de existir. |
