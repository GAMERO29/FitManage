# ADR N.° 03 · Una sola aplicación Django con plantillas en el servidor y una API mínima para la caché sin conexión

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado (30/10/2026) |
| Contexto | El DAD ya proponía un monolito modular, pero esa decisión nunca se registró con alternativas. Antes de escoger el estilo interno (siguiente guía) hay que fijar cómo se divide y se despliega el sistema. Fuerzas: los drivers del ADR N.° 02 (fiabilidad de pagos y fechas, consulta disponible en recepción, seguridad), un solo desarrollador, costo cero (R-01), navegador sin apps nativas (R-02), internet inestable (R-03) y la regla de que un pago y su evento de auditoría se guardan en la misma transacción. |
| Alternativas consideradas | **A. Una aplicación Django:** plantillas en el servidor, Bootstrap, Service Worker con caché de solo lectura y un único endpoint JSON `/api/v1/estados/` para llenar esa caché. **B. API REST en Django + SPA en React:** dos proyectos, dos despliegues y la autorización repartida entre la API y el cliente. **C. Microservicios:** socios, membresías, pagos y notificaciones por separado, con una base de datos por servicio y mensajería entre ellos. |
| Matriz (alto/medio/bajo) | Fiabilidad de pagos y fechas: A alto, B alto, C bajo. Disponibilidad de la consulta sin conexión: A alto, B alto, C medio. Seguridad del acceso y los datos: A alto, B medio, C medio. Costo y esfuerzo para un desarrollador (desempate): A alto, B medio, C bajo. |
| Decisión | FitManage se construye y se despliega como una sola aplicación Django (alternativa A). |
| Consecuencias | A favor: el pago y su auditoría quedan en una transacción de PostgreSQL (QA-05 sin transacciones distribuidas); la autorización por rol vive en un solo lugar del servidor (QA-04); un solo despliegue en la capa gratuita del PaaS (R-01); el Service Worker cubre QA-02 sin necesitar una SPA. En contra: la interfaz será menos dinámica que una SPA; si algún día se necesita una app móvil, habrá que crecer la API; todo escala junto, lo cual está bien para 1 a 3 equipos por gimnasio pero obligaría a revisar este ADR con varias sedes. |
| Alternativas descartadas | **B** se descarta porque duplica proyectos y despliegues para un solo desarrollador y reparte la autorización entre dos lugares, sin mejorar ningún driver: la consulta sin conexión ya la resuelve el Service Worker. **C** se descarta porque rompe la transacción pago + auditoría (exigiría sagas y consistencia eventual justo donde está el driver número uno), multiplica la infraestructura que habría que pagar y vigilar, y resuelve un problema de escala que un gimnasio de barrio no tiene. |
