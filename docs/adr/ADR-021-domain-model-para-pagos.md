# ADR N.° 21 · Las reglas de pagos y anulaciones se quedan en un Domain Model

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado (27/11/2026) |
| Contexto | En la Software III (Guía 12) surgió la sospecha de sobreingeniería: ¿hace falta `Pago`, `Periodo`, `HistorialPagos` y una `PoliticaAnulacion` para lo que en el fondo son dos tablas? Para responderla escribí la anulación también como Transaction Script (`docs/sw3/g12/experimento/transaction_script.py`, 81 líneas, tres procedimientos) y corrí los mismos casos sobre las dos versiones, con el mismo estado inicial. Después introduje el mismo cambio de regla en las dos (CR-02: motivo con al menos 5 caracteres). |
| Alternativas consideradas | **A. Transaction Script:** un procedimiento por operación (anular el último, anular por id y anular para cambio de plan). Es directo y fácil de leer de arriba abajo, pero la regla de rol aparece 3 veces, la del último vigente 2 (más una variante), la de la recepcionista 2 y la del motivo 3. **B. Domain Model (actual):** cada regla está una vez: el motivo y la transición en `Pago.anular`, el último vigente en `HistorialPagos`, quién puede anular en `PoliticaAnulacion` y la coordinación en `AnulacionPagoService`. El costo es más archivos, interfaces y el mapeo ORM ↔ dominio (`persistencia/mapeo.py`). |
| Matriz de decisión | **Casos equivalentes:** los tres pasan en las dos versiones (`experimento_antes_cr02.txt`). **Cambio CR-02:** en A, 3 lugares y 12 líneas; en B, 1 lugar y 7 líneas, más una prueba (`impacto_cambio.txt`). **Riesgo de olvido:** en A, si se cambia 2 de 3 copias la prueba del experimento solo lo detecta porque está parametrizada por entrada; en producción esa prueba no existiría por cada vista. **Lectura:** A gana en un flujo aislado; B gana cuando la misma regla se usa en varias entradas. |
| Decisión | Se mantiene el Domain Model para pagos, anulaciones y cambios de plan. Los modelos de lectura (`infraestructura/consultas.py`: recepción, reportes, auditoría) siguen como scripts de consulta, porque no cambian estado ni comparten invariantes. |
| Consecuencias | Positivas: CR-02 se implementó en un lugar y la pantalla, el contrato y el dominio dicen lo mismo. Negativas: un desarrollador nuevo tiene que recorrer cuatro clases para entender la anulación; lo mitiga el diagrama de secuencia de la Guía 08. Trade-off aceptado: más estructura a cambio de que cada regla viva en un solo lugar. |
| Condición para reconsiderar | Si un flujo nuevo tiene una sola entrada, no comparte reglas con otro y no cambia estado de pagos (por ejemplo, exportar un CSV), se escribe como Transaction Script. Si un flujo hoy escrito como script de consulta empieza a escribir o a repetir una regla de `dominio/`, pasa al modelo. |
| Alternativas descartadas | A, porque el experimento mostró que la duplicación crece con cada entrada: el cambio de plan agregó la tercera copia de todo. La observación vale para este flujo y no se generaliza a todo FitManage. |
